# Day 12 - DHCP: How Your Device Gets an IP
**Date:** 2026-08-27

## 1. Key Concepts Learned (1.5h Theory and labs)

* **DHCP (Dynamic Host Configuration Protocol):** Automatically assigns a private IP address (and related config) to a device joining a network, so it doesn't need to be manually set up.

* **DHCP is built on top of BOOTP (Bootstrap Protocol)** — an older protocol. This is why DHCP packets still show BOOTP header fields, and why tcpdump literally labels DHCP packets as "BOOTP/DHCP."

* **BOOTP header field full forms (the older, structural fields DHCP inherited):**
  - **`op`** = Operation code (`BOOTREQUEST` from client, `BOOTREPLY` from server)
  - **`htype`** = Hardware type (1 = Ethernet)
  - **`hlen`** = Hardware address length (6 for a MAC address)
  - **`xid`** = Transaction ID — a random number generated by the client to match up all packets (Discover/Offer/Request/Ack) belonging to the same negotiation
  - **`ciaddr`** = Client IP address (only filled in if the client already has a valid IP, e.g. during a renewal)
  - **`yiaddr`** = "Your" IP address — the IP the server is offering/assigning to the client
  - **`siaddr`** = Server IP address — the DHCP server's own IP
  - **`giaddr`** = Gateway/Relay IP address — used only if a DHCP relay agent sits between client and server (0.0.0.0 if not applicable)
  - **`chaddr`** = Client hardware address — the client's MAC address (this is how the server knows who to reply to, since the client doesn't have an IP yet at the start)

* **DORA — the 4-step DHCP lease process** (client always broadcasts, since it has no IP yet):
  1. **D — Discover:** Client broadcasts "I need an IP" to `255.255.255.255`, includes a wishlist (`Parameter-Request`) of options it wants (subnet mask, gateway, DNS server, etc.)
  2. **O — Offer:** A DHCP server replies with a proposed IP (in `yiaddr`/"Your-IP") and lease terms. The server decides the actual lease duration — the client's requested lease time is just a suggestion.
  3. **R — Request:** Client broadcasts back "I accept this specific offer from this specific server" (naming `Server-ID` and `Requested-IP`) — broadcast so that if multiple servers offered, the ones not chosen know to withdraw.
  4. **A — Ack (Acknowledge):** Server confirms the lease is finalized — same lease details repeated, now binding.

* **Vendor-rfc1048 Extensions:** The actual DHCP-specific data sits in this block, separate from the older BOOTP header fields. Named after RFC 1048, the spec that originally defined these "vendor extensions" to BOOTP, later adopted as DHCP's option format. Includes: `DHCP-Message` (which DORA step this is), `Lease-Time`, `Subnet-Mask`, `Default-Gateway`, `Domain-Name-Server`, etc.

* **Lease timers — three key numbers, all counted from lease start:**
  - **Lease-Time:** Total duration the IP is valid (seen: 86400s = 24 hours)
  - **T1 / Renewal time (RN):** 50% of lease time (43200s = 12h) — client quietly tries to renew with the *original* server
  - **T2 / Rebinding time (RB):** 87.5% of lease time (75600s = 21h) — if T1 renewal failed, client now broadcasts to *any* DHCP server as a fallback

* **DHCP Release:** A client can voluntarily give back its IP before the lease expires (`DHCP-Message: Release`) — this is what happens when forcing a manual renewal, and it's the step that happens *before* a fresh DORA cycle begins.

## 2. Command Flags Reference (so this never needs re-Googling)

**`ipconfig` commands:**
```bash
ipconfig getpacket en1        # view the current DHCP lease details for an interface
sudo ipconfig set en1 DHCP    # release current lease and force a fresh DORA negotiation
```

**`tcpdump` flags used today (and their actual meaning):**
| Flag | Full meaning | What it does |
|---|---|---|
| `-n` | Numeric | Show raw IPs/ports, don't resolve to hostnames |
| `-e` | Ethernet/link-layer header | Show source & destination MAC addresses |
| `-i` | Interface | Specify which network interface to capture on (e.g. `en1`) |
| `-v` | Verbose | Show full protocol decode — for DHCP, this reveals the actual message type (Discover/Offer/Request/Ack) and every option field, instead of just a generic "Request"/"Reply" summary line |

**Key lesson on `-v` specifically:** without it, tcpdump's DHCP output just says "Request" or "Reply" for every packet — impossible to tell Discover from Request, or Offer from Ack, since they share the same base BOOTP message type. `-v` unlocks the actual `DHCP-Message` field inside Vendor Extensions, which is the real indicator of which DORA step you're looking at.

## 3. Hands-on Lab & Commands
```bash
# View current DHCP lease
ipconfig getpacket en1

# Force a lease release + fresh DORA cycle
sudo ipconfig set en1 DHCP

# Capture the handshake — first pass, without -v (too generic to be useful)
sudo tcpdump -n -i en1 -e port 67 or port 68

# Capture again — with -v, full DORA process clearly labeled
sudo tcpdump -n -i en1 -v port 67 or port 68
```

## 3. Key Takeaway / Blocker Solved

Blocker Solved: With just `-e` (no `-v`), tcpdump's DHCP output only shows generic "Request"/"Reply" labels — indistinguishable between Discover/Request or Offer/Ack. Re-ran with `-v` instead, which decodes the actual `DHCP-Message` field and revealed the full, correctly-labeled DORA sequence: Release (from the forced renewal) → Discover (x2, one retry) → Offer (x2) → Request → Ack.

Also worked out a structural nuance: the offered IP (`Your-IP`) sits in the older BOOTP header fields, *above* the DHCP-specific `Vendor-rfc1048 Extensions` block — not buried inside the DHCP options themselves. This reflects DHCP's actual design: it's built directly on top of BOOTP's original packet structure, reusing fields like `yiaddr`/`siaddr`/`chaddr`, and only *adds* DHCP-specific metadata (message type, lease time, requested options) as a separate "vendor extension" block per RFC 1048.

Captured a real lease from Day 12's `getpacket` output and matched every timer value (lease time, T1, T2) against the same fields seen live in the tcpdump capture — confirming these aren't separate concepts, just two different views (static snapshot vs. live packet) of the exact same lease.
